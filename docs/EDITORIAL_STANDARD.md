# Editorial standard

Every article is an operational artifact, not a list of commands. It must make assumptions, risk, ownership, evidence, and recovery explicit.

## Required structure

- Purpose, audience, and measurable learning objectives
- Supported or tested versions and known limits
- Prerequisites, permissions, backups, and recovery access
- Architecture, trust boundaries, and failure domains
- A staged implementation with placeholders clearly identified
- Validation commands and expected evidence
- Failure modes and a diagnostic sequence
- Rollback or forward-recovery procedure
- Monitoring, alert ownership, capacity, and cost implications
- A safe lab, exercise, or decision record for advanced material
- Claim-level links to current first-party sources

Commands must be safe to copy only after placeholders are replaced. Destructive actions require a warning immediately before the command, positive target identification, and a verified recovery path.

## Review evidence

Record the reviewer, verification method, verification date, tested versions, source scope, and change summary. Documentation review and lab execution are different evidence types and must not be represented as equivalent.

## Voice and accessibility

Use direct language, explain acronyms on first use, avoid unexplained vendor terminology, and never use color as the only status signal. Headings must be unique and ordered logically. Link text must identify its destination.
